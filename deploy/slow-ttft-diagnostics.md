# 慢首字链路诊断

HTTP 流式 OpenAI 请求从第一次开始转发到首次有效内容超过 10 秒时，
沿用 `logs/slow-ttft/slow-YYYYMMDDTHHmmZ.jsonl` 记录诊断。
没有有效输出的慢请求也记录。正常首字但完成时间很长的请求不记录。
无需额外开关；需要运行包含本改动的二进制才会有新增字段。

保留 1 小时，每分钟清理（无请求也执行）；每分钟文件最多 128 KiB，
总量约 8 MiB；每条记录最多 16 KiB。达到分钟上限会丢弃新记录，
下一条成功记录用 `dropped_since_last_record` 标明数量。
多次重试导致记录过大时，优先裁剪旧尝试的活动桶、事件明细、IO 明细，
并标记 `stream_detail_truncated`，保留原有请求时间节点。

## 时间和边界

所有 `*_ms` 时间点均相对 `received_at`（应用入口中间件），不是用户点击发送时间。
保留原有 DNS、连接、响应头、首 SSE、首有效内容、本地 Flush 等节点。
新增 `upstream_headers_ms` 位于显式解压之前，旧 `response_headers_ms`
位于传输函数返回后；某些解压器初始化会在这两点之间读取压缩头。

`stream_io` 提供四层统计，各有调用次数、字节数、首末进展时间、
最长进展间隔及起止时间、最长调用耗时及起止时间、错误次数：

- `raw_body_read`：TLS 解密和 HTTP 分帧之后、程序显式解压之前的 HTTP body 读取。
  不是 TCP 包，也不能单凭其间隔证明网络丢包。
- `decoded_body_read`：传输层返回给 SSE 扫描器的 body 读取。
  若解压失败或编码不受支持，它也可能仍然是编码后的数据。
- `downstream_write`：程序向本地响应 writer 写数据，包含心跳；不是客户端收包确认。
- `downstream_flush`：本地 Flush 调用，包含心跳。接口没有错误返回值，
  因此其零错误计数不表示网络送达成功。

`body_encoding` 只记录固定类别，`upstream_protocol` 只记录 HTTP 协议版本。
若 Go transport 已自动解压，编码标记为 `transport_decoded`，无法再观察压缩前边界。
如果插件等路径未经过此处的仓库传输层，解压前字段缺失，不能当作零。
原生 raw HTTP/1.1、HTTP/2 及标准 Go transport 都已接入。

**读取耗时是嵌套的**：解压后 Read 可能包含等待上游数据的时间。
不能把两层总耗时相加，或简单相减后当成解压 CPU 时间。
`max_gap_ms` 是有数据的读取/写出之间的间隔，也会受调用方暂停读取影响；
`max_call_ms` 是单次 Read/Write/Flush 从进入到返回的时间。
EOF 不计为读取错误，没有数据的 EOF 不更新最后数据时间。

## 中途活动

- `sse_events`：固定白名单事件类型，值按 `sse_event_columns`
  表示 `[次数, 首次毫秒, 最后毫秒]`。未知类型归入 `other`，注释归入 `comment`。
- `first_content_event_type` / `first_content_kind`：首个有效内容的事件类型和类别，
  区分 text、reasoning、tool、image 或 other；不会把元数据/心跳算成有效输出。
- `stream_activity`：按 `stream_activity_columns` 表示
  `[开始毫秒, 结束毫秒, 解压前字节, 解压后字节, SSE次数, 写出字节, Flush次数]`。
  每个尝试固定 24 个桶，前 23 个为 5 秒，最后一个汇总 115 秒后的全部活动；
  空桶省略。持续很久的请求不会增加内存，不能把末桶误读成普通 5 秒桶。

例如：原始读取持续有数据、解压后迟迟无数据，重点检查编码/解压边界；
解压后已有数据而有效 SSE 很晚才出现，检查事件内容类别、分帧和处理排队；
有效 SSE 很早而本地 Write/Flush 很晚完成，检查本地写阻塞。
如果各层都在末尾集中出现内容，需进一步区分上游生成方式和接收链路，
这些统计不能单独证明模型一直在思考。

每个尝试仅固定数组和数值统计，不保存提示词、回复、工具参数、密文、
认证头、原始错误文本或任意上游事件名称。请求最多保留前 7 次和最近 1 次尝试。
普通 Responses、透传、Responses 转 Chat 路径沿用原有 TTFT 口径和输出行为。

## 上传尚未完成的请求

请求体没有收完时还未进入上游转发，不能用上面的慢首字日志解释。
已有 `read request body failed` 警告在共享读取器失败时另带
`bytes_read`（解压前实际读取字节）、`read_ms`（本次完整读取过程耗时），
声明长度不小于已读长度时带 `content_length_gap_bytes`。
同时记录固定类别的 HTTP 协议、编码和是否使用 chunked。
没有观测到的计数省略，未知长度不推算缺失字节；不记录请求内容或原始错误文本。
这些字段沿用已有错误日志和清理规则，不新增按请求保留的内存缓存。

真实读取超时用 `read_timeout` 区分于 `truncated_body` 和
`client_disconnect`；对客户端仍沿用现有 408 提示，体积超限保持 413。
读取耗时不是最后一次收包到断开之间的空闲时间，缺失字节数本身也不能确定哪层断开。
前置代理提前终止上传时，应用看到的连接对端可能是代理，不能直接归责给最终用户。
